# Nudge database v3.1: validation specification (every field of every table)

How to read this. Each row has two columns of rules.

- **Database enforces**: read directly from the live PostgreSQL catalog, so it is exactly what the database refuses. Nothing here depends on the application being correct.
- **Serializer / service must also enforce**: real-world rules the database cannot express (valid email shape, real time zone, real currency, password strength, ownership of ids, state rules). Rules that come from the SRS are marked by the SRS section in the text; the others follow normal good practice and are for the team to confirm.

Why two layers. The database is the last line of defence and the only one that cannot be bypassed, but its errors are not user friendly and composite-FK violations appear only at commit. The serializer gives the user a clear 400 message first. A rule listed in only one layer is a gap.

Three rules that apply to every table:

- organization_id and id are never taken from the request body.
- Every id sent by the client is looked up inside request.organization first.
- Text is stripped, and the NUL character and control characters are rejected before saving (PostgreSQL cannot store NUL).
